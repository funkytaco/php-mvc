Database Connector

How a git-sourced app gets a database: which engine Nimbus provisions, how it seeds from a SQL file already in your repository, how to use a file-backed database instead of a container, and how the credentials actually reach the app.

Design spec · not yet built

Everything on this page is the proposed contract, written against the real behaviour of the repositories in .installer/repos/. Today features.database is false for every git app and the compose builder emits Postgres only — which is why blog reports no database connection.

Why blog reports no connection

Two independent causes, and the second one bites even after you add a database container.

Cause 1 · no database exists

Git apps are created with features.database: false, so no database service is emitted at all. Even if it were flipped on, buildDatabaseService() only knows how to write a postgres:14 block — and WordPress speaks MySQL.

Cause 2 · Bedrock never reads the credentials

Bedrock wraps its entire dotenv block in if (file_exists($root_dir . '/.env')) (config/application.php:43). With no .env file in the repository, DB_NAME, DB_USER and DB_PASSWORD are never defined and WordPress falls back to nothing. Setting container environment variables alone does not fix this — the file has to exist.

Consequence for the design

Provisioning an engine is the easy half. The connector is only useful if it also delivers credentials in the shape the framework expects — which differs per framework, and for Bedrock means writing a real .env file.

01 Four shapes a database can take

One engine value selects between them. The first two provision a container; the second two never do.

Server · provisioned Engine container, empty Nimbus runs mariadb, mysql or postgres from an official image, generates a password, and waits for its healthcheck before starting the app. The app migrates or installs into it. engine: "mariadb" · Laravel with migrations
Server · seeded Engine container + your SQL The same, plus a .sql file already in your repository mounted into the image's init directory so it runs on first boot. This is how you point at an existing schema or dump. engine + init: "database/seed.sql"
File · in-repo SQLite file No container at all. Nimbus points the app at a file inside the repository, creates it if missing, and makes sure it stays writable and survives rebuilds. Laravel ships configured for exactly this. engine: "sqlite" · file: "database/database.sqlite"
External Somebody else's database Nimbus provisions nothing and only injects the connection details you give it — a database on your host, in another compose stack, or a managed one. engine: "none" + explicit env

02 The database block

Declared in the repository's .nimbus.json, alongside docroot and the rest — same file, same precedence rules (command line beats manifest beats detection beats default).

All keys optional. Omitting the whole block keeps today's behaviour: no database.
KeyMeaningDefault
engine mariadb, mysql, postgres, sqlite, or none. "none"
version Image tag for the engine. Ignored for sqlite/none. per engine
name Database name to create. <app>_db
user User to create. The password is always generated and vaulted — never written here. <app>_user
init Repo-relative .sql (or .sh) run on first boot of an empty database. Your existing schema or dump. detected
file Repo-relative SQLite file. Only meaningful when engine is sqlite. detected
containerfile Build the database image from your own definition instead of pulling an official one. Rarely needed — see below. null
env How credentials reach the app: a preset name (bedrock, laravel) or an explicit variable map. detected
env_file Repo-relative file Nimbus writes the resolved variables into. Required by Bedrock. ".env" if the repo has .env.example
On building a Containerfile for the database

Official engine images already accept a database name, user, password and an init directory — everything a fresh instance needs — so containerfile is the escape hatch, not the path of least resistance. Reach for it when you need an extension, a locale, a tuned my.cnf, or seed data baked into the image rather than replayed on boot. Everything else is better expressed as init.

03 Getting credentials into the app

The part that actually fixes blog. Nimbus generates one password and then has to express it in whatever dialect the framework reads.

Presets

Left column is what Nimbus resolves; the rest is what each framework expects to see.
Nimbus value bedrock laravel
hostDB_HOSTDB_HOST
port—DB_PORT
nameDB_NAMEDB_DATABASE
userDB_USERDB_USERNAME
passwordDB_PASSWORDDB_PASSWORD
driver—DB_CONNECTION
Why a map and not a fixed set

Bedrock reads DB_NAME and DB_USER; Laravel reads DB_DATABASE and DB_USERNAME and additionally needs DB_CONNECTION switched away from its sqlite default. Same database, different vocabulary — so the mapping is the contract, and a preset is just a named one.

Delivery: file and container, not either/or

Nimbus writes the resolved variables to env_file inside the repo and sets them as container environment variables. The file is what Bedrock requires; the environment is what a twelve-factor app expects. Doing both costs nothing and removes a whole class of "works in one framework" bugs.

This writes into your working tree

.env holds a real generated password, so it lands in the clone — the one place Nimbus otherwise keeps clean. Every framework that wants a .env already gitignores it, and Nimbus should refuse to write the file if the repository does not, rather than risk it being committed.

Where the password comes from

Nothing new. PasswordManager and VaultManager are already source-agnostic — the resolution order (vault, then a running container, then an existing data volume, then generate) and the automatic vault backup work unchanged for git apps.

  1. First VaultRestore the credentials this app was created with, so a recreate reconnects to its existing data.
  2. Then Running containerRead them back off the live database container via podman inspect.
  3. Then Existing volume or compose fileAdopt what the on-disk data was initialised with, rather than orphaning it.
  4. Last GenerateA new password, backed up to the vault automatically.

04 Pointing at a database file already in the repo

"A database file in the repository" means two genuinely different things, and the connector supports both.

A SQL file that seeds a server

A schema or a dump, replayed once into an empty database. Mounted into the engine image's init directory, which runs every .sql and .sh it finds on first boot — and only when the data directory is empty. 

{
  "database": {
    "engine": "mariadb",
    "init": "database/seed.sql"
  }
}

Detected automatically when absent, in order: database/schema.sql, database/init.sql, database/dump.sql, schema.sql. Nimbus reports which it picked, the same way it reports the document root.

A SQLite file that is the database

Not seed data — the live database. No container, no password, no healthcheck. Nimbus creates the file if missing, keeps it writable by the web user, and makes sure a rebuild cannot silently discard it. 

{
  "database": {
    "engine": "sqlite",
    "file": "database/database.sqlite"
  }
}
Only safe in dev mode

A built image holds a copy of the file, so writes vanish on rebuild. Under bin/nimbus dev the clone is bind-mounted and the file is the real one on your disk. Nimbus should warn when SQLite is paired with a non-dev run.

The seeding trap

Init files run only against an empty data directory. Change your .sql after the first boot and nothing happens — the database already exists, so the image skips initialisation entirely. Re-seeding means removing the volume (nimbus:delete with volumes, or podman volume rm). This surprises people every time, so the CLI should say it out loud when it mounts an init file.

05 Worked examples

Bedrock / WordPress — what blog needs

MariaDB, credentials delivered as a .env file because Bedrock will not read them otherwise. 

// .installer/repos/bedrock/.nimbus.json
{
  "docroot": "web",
  "database": {
    "engine": "mariadb",
    "version": "11",
    "name": "wordpress",
    "user": "wordpress",
    "env": "bedrock",
    "env_file": ".env"
  }
}

Nimbus writes, alongside the WP_HOME and salts Bedrock also requires:

# .installer/repos/bedrock/.env  (generated, gitignored by Bedrock)
DB_NAME='wordpress'
DB_USER='wordpress'
DB_PASSWORD='<generated, vaulted>'
DB_HOST='blog-db'
WP_HOME='http://localhost:8531'
WP_SITEURL='http://localhost:8531/wp'
Bedrock needs more than credentials

Its dotenv block also does $dotenv->required(['WP_HOME','WP_SITEURL']), so the connector has to fill those from the app's resolved port or WordPress still refuses to boot. The bedrock preset should own that, since it is the same class of problem.

Laravel — file-backed, no container

// .installer/repos/laravel/.nimbus.json
{
  "docroot": "public",
  "database": {
    "engine": "sqlite",
    "file": "database/database.sqlite",
    "env": "laravel"
  }
}

Which yields DB_CONNECTION=sqlite and an absolute DB_DATABASE pointing inside the container — and no database service in the compose file at all. Swapping to "engine": "mariadb" switches DB_CONNECTION and adds the container, with no other edits.

06 What Nimbus generates

For the Bedrock example, added to blog-compose.yml. The app waits on the healthcheck, so WordPress never starts against a database still coming up. 

services:
  blog-app:
    build:
      context: "./.installer/repos/bedrock"
      dockerfile: Containerfile
    environment:
      DB_HOST: blog-db
      DB_NAME: wordpress
      DB_USER: wordpress
      DB_PASSWORD: <generated>
    depends_on:
      blog-db:
        condition: service_healthy
    ports: ["8531:80"]

  blog-db:
    image: "mariadb:11"
    container_name: blog-db
    environment:
      MARIADB_DATABASE: wordpress
      MARIADB_USER: wordpress
      MARIADB_PASSWORD: <generated>
      MARIADB_ROOT_PASSWORD: <generated>
    volumes:
      # persistent data — see the gotcha below
      - "./data/blog:/var/lib/mysql:Z"
      # only when database.init is set
      - "./.installer/repos/bedrock/database/seed.sql:/docker-entrypoint-initdb.d/10-seed.sql:Z"
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"]
      interval: 5s
      retries: 10
    networks: [blog-net]
Fix this while you are in here

The existing Postgres builder has its data volume commented out (AppManager::buildDatabaseService()) — so today every template app's database is ephemeral and loses everything on down. The new engines should mount persistent storage from the start, and the Postgres path should be fixed to match rather than have the inconsistency copied forward.

07 What it takes to build

The hierarchy already has the seams; this mostly fills them in.

ChangeWhereNote
Engine-aware service AppManager::buildDatabaseService() Split per engine — env var names, healthcheck and data path all differ. Postgres behaviour must stay byte-identical for template apps.
Manifest keys GitAppManager::MANIFEST_KEYS Accept database as a nested block; resolve it in resolveRepoSettings() with the existing precedence.
Engine detection GitAppManager Infer from the repo: DB_CONNECTION in .env.example, a wp-cli.yml, an artisan file, a committed .sql.

App service env GitAppManager::buildAppService() Add the mapped variables and the depends_on: service_healthy edge.
Flip the default GitAppManager::writeGitAppConfig() features.database becomes true whenever engine is a server engine.

Open questions worth deciding first

Should Nimbus write into the clone at all?

Writing .env breaks the "never touch the working tree" rule the git flow was built on — the generated Containerfile is the only other exception. The alternative is mounting a generated .env from the instance directory over the repo path at runtime, which keeps the tree clean but means the file is missing when you run the app any other way.

One password or two?

MySQL and MariaDB have a root password distinct from the app user's. PasswordSet models a single database password today, so either it gains a field or the root password is derived and never surfaced.

Where does data live?

Template apps use ./data/<app> (currently disabled). A named podman volume is more portable across machines; a bind mount is easier to inspect and back up. Pick one and apply it to both paths.
