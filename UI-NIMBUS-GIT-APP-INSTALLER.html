Nimbus · containerize a git repository

Git App Installer

Point Nimbus at a PHP repository and it clones, containerizes and runs it under podman — reusing the same compose, port, registry and dev-mode machinery that template-scaffolded apps use. This page covers the install flow and the .nimbus.json contract a repository can ship to control it.

$ bin/nimbus create-from-git blog https://github.com/roots/bedrock.git

What happens, end to end

The clone and the app instance are deliberately kept apart: your working tree stays clean, and one clone can back several app instances.

Source Your repository A clone URL, or a repo already sitting in repos/. github.com/you/app.git
Clone Shared checkout Cloned once, shallow. Gitignored. Never written to by Nimbus except a generated Containerfile. .installer/repos/<repo>/
Instance Nimbus-owned config Holds app.nimbus.json — ports, resolved settings, feature flags. .installer/apps/<app>/
Run Compose stack Built from the clone, served by podman on a port derived from the app name. <app>-compose.yml

01 Install an app

Three commands take you from a URL to a running container. Each is idempotent enough to re-run; a failed create rolls back its instance directory and registry entry, leaving the clone in place.

  1. Create

    Clones the repository and writes the app's config. If the repo already exists under .installer/repos/, it is adopted as-is rather than re-fetched — so a clone you made by hand works fine. 

    $ bin/nimbus create-from-git blog https://github.com/roots/bedrock.git

# adopt an existing clone by name instead of a URL
$ bin/nimbus create-from-git blog bedrock

# pin a branch or tag, and override what was detected
$ bin/nimbus create-from-git blog https://example.com/app.git \
    --ref=v2.1.0 --docroot=web

    Read the notices it prints. They tell you the document root it chose, which Containerfile it used, and whether it generated one for you.

  2. Install

    Generates <app>-compose.yml. For a git app this is compose-only — there is no asset map to copy, because the code stays in the clone and is built from there. 

    $ bin/nimbus install blog

  3. Run

    Builds the image from the clone and starts it. Use dev instead to bind-mount the clone over the container's web root — edits on the host are live, and a code-server sidecar gives you VS Code in the browser on the same tree.

    Dependencies on the first dev run

    Mounting the clone replaces everything the image built at that path, including vendor/ — which every PHP repo gitignores, and which for Bedrock is where WordPress core itself lives. So dev mode runs composer install on start when the directory is missing, putting the dependencies on the host side of the mount where they persist and stay editable. Later starts skip it. 

    $ bin/nimbus up blog          # built image, no mounts
$ bin/nimbus dev blog         # live-edit + code-server
$ bin/nimbus status
Either interface works

bin/nimbus <cmd> runs the file-generating commands inside the nimbus-tools container. If you have PHP and Composer locally, composer nimbus:create-from-git blog <repo> and friends do the same thing directly.

02 Where everything lives

.installer/repos/ is the git analogue of .installer/_templates/ — it holds source, not instances. 

php-mvc/
├── .installer/
│   ├── repos/                  ← clones live here (gitignored)
│   │   └── bedrock/
│   │       ├── .git/
│   │       ├── .nimbus.json         ← YOUR manifest goes here (repo root)
│   │       ├── Containerfile          yours, or generated by Nimbus
│   │       ├── composer.json
│   │       └── web/                   detected as the document root
│   │           └── index.php
│   └── apps/
│       └── blog/
│           └── app.nimbus.json ← Nimbus-owned; resolved settings + ports
└── blog-compose.yml            ← generated stack
Why they're separate

Nothing generated and no resolved password ever lands inside your working tree, so git status in the clone stays clean and there is nothing to accidentally push upstream. The one exception is a Containerfile Nimbus generates for you — which you are meant to review and commit.

03 Writing a .nimbus.json by hand

Optional. Without one, Nimbus detects what it can and assumes the rest. Add one when detection gets it wrong, or when you want the repository itself to declare how it should be containerized — so anyone installing it gets the same result.

Location

At the root of the repository, committed alongside composer.json — not in the app instance directory. On disk that is .installer/repos/<repo>/.nimbus.json; in your project it is simply .nimbus.json at the top level.

A complete example

{
  "runtime": "php",
  "docroot": "web",
  "containerfile": "Containerfile",
  "container_port": 80,
  "webroot": "/var/www/html"
}

The minimum worth writing

Most repositories only need to correct the one thing detection cannot infer: 

{
  "docroot": "httpdocs"
}

Every accepted key

Unknown keys are ignored with a notice, not an error.
KeyMeaningDefault
runtime Which stack of defaults to use. php is the only one today. "php"
docroot Directory inside your repo that the web server serves. Empty means the repo root. Must exist, or create fails. detected
containerfile Path to your image definition, relative to the repo root. "Containerfile"
container_port Port your image listens on inside the container. 80
webroot Path inside the container the code is served from. Also where dev mode bind-mounts the clone. "/var/www/html"
command How to start the server, if your image is not Apache. Dev mode otherwise tries apache2-foreground then php-fpm -F. detected
Watch the two roots

docroot is relative to your repo (web). webroot is absolute inside the container (/var/www/html). Apache ends up serving the two joined: /var/www/html/web.

What Nimbus writes for you

Your manifest is an input. The resolved result is recorded in the app's own app.nimbus.json, which is where the compose builder reads from: 

{
  "name": "blog",
  "source": {
    "kind": "git",              ← selects GitAppManager on every later command
    "repo": "bedrock",
    "url":  "https://github.com/roots/bedrock.git",
    "ref":  null,
    "runtime": "php",
    "docroot": "web",
    "webroot": "/var/www/html",
    "container_port": 80,
    "containerfile": "Containerfile"
  },
  "features": { "database": false, "eda": false, "certbot": false, "keycloak": false },
  "containers": { "app": { "port": "8531" } }
}
Note the missing key

A git app has no type. That key means "template directory name" everywhere else in Nimbus, so it is deliberately left off — source.kind is what identifies a git app. An app with no source block at all is treated as template-scaffolded, which is why every app created before git support keeps working untouched.

04 Resolution order

Four sources can decide any setting. The highest one that has an opinion wins.

  1. Strongest Command-line flag A one-off override for this install: --docroot=public. Accepted flags are --ref, --repo, --runtime, --docroot, --webroot and --containerfile.
  2. Then .nimbus.json The repository's own declaration. The only place container_port can be set — there is no flag for it.
  3. Then Detection What Nimbus can infer from the tree: the document root, an existing Containerfile, the PHP version in composer.json.
  4. Fallback Runtime default For php: image php:8.3-apache, web root /var/www/html, port 80.

05 What Nimbus works out on its own

Document root

Checked in order for an index.php; the first hit wins, otherwise the repository root is served.

Looks forTypical ofResult
web/index.phpRoots Bedrock (WordPress)docroot: "web"
public/index.phpLaravel, Symfony, Slim appsdocroot: "public"
html/index.phpOlder PHP layoutsdocroot: "html"
— none —Libraries, flat projectsdocroot: "" (repo root)

Image definition

Nimbus looks for Containerfile then Dockerfile, at the repository root only. If neither exists it writes one and tells you.

A .devcontainer image is not adopted automatically

A .devcontainer/ definition describes an IDE environment, not necessarily a servable one — Bedrock's is php-fpm with no web server, paired with a separate nginx service in its own compose file. Building that as your app container gives you something that starts and serves nothing. Nimbus points out that it exists and generates a real image instead; pass --containerfile=.devcontainer/Dockerfile to use it anyway.

The generated Containerfile

Derived from what your repository actually declares — the PHP version and any ext-* from composer.json, plus the detected document root. It is written into the clone as a starting point for you to review, adapt and commit; it is not a production image. 

# generated for Bedrock: php >=8.3, docroot web/
FROM php:8.3-apache

RUN apt-get update && apt-get install -y --no-install-recommends \
        git unzip zip libzip-dev libicu-dev \
    && docker-php-ext-install -j"$(nproc)" pdo_mysql mysqli zip intl \
    && apt-get clean && rm -rf /var/lib/apt/lists/*

COPY --from=composer:2 /usr/bin/composer /usr/local/bin/composer

ENV APACHE_DOCUMENT_ROOT=/var/www/html/web
RUN sed -ri -e 's!/var/www/html!${APACHE_DOCUMENT_ROOT}!g' /etc/apache2/sites-available/*.conf \
    && sed -ri -e 's!/var/www/!${APACHE_DOCUMENT_ROOT}!g' /etc/apache2/apache2.conf /etc/apache2/conf-available/*.conf

RUN a2enmod rewrite

WORKDIR /var/www/html
COPY . /var/www/html

RUN composer install --no-interaction --prefer-dist --no-progress --no-scripts

RUN chown -R www-data:www-data /var/www/html

06 What git apps can and cannot do yet

Git apps inherit the whole generic lifecycle. What they do not inherit is anything that needs template scaffolding a bare repository does not have.

CapabilityStatusDetail
up / down / status Works Identical to template apps — same compose, ports and container naming.
dev mode Works Bind-mounts the clone at webroot, plus a code-server sidecar on the same tree.
delete Works Removes the instance, compose file and registry entry. The clone in repos/ is left alone.
commit No-op There is no template to copy edits back to. Safe to run; it tells you to use git commit in the clone.
database Off by default The compose builder only emits Postgres, and these apps generally want MySQL/MariaDB. Bring your own for now.
EDA / Keycloak Refused Both mount files that come from a Nimbus template. You get a clear error rather than a crash-looping container.

07 Verify and troubleshoot

Confirm what was resolved

$ cat .installer/apps/blog/app.nimbus.json
$ cat blog-compose.yml

The compose file's build.context should point at ./.installer/repos/<repo>, and its port mapping should end in your container_port.

Common outcomes

Document root '…' does not exist
A docroot you declared or passed is not a directory in the repo. Check spelling and that it is committed.
Container starts but serves nothing
Usually a php-fpm image with no web server. Use the generated Containerfile, or add a web server to your own.
Feature '…' is not supported for git-sourced apps
EDA and Keycloak need template scaffolding. Expected — see the table above.
Changes not showing up
up serves a built image. Use bin/nimbus dev <app> for live edits, or rebuild.
